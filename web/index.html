What is Keyhole?

Watch it happen →

Of 24 major NEAR contracts Keyhole surveyed (the trust table below), 11 are governed by a Sputnik DAO, among them Ref, Burrow, Meta Pool and LiNEAR, and none is immutable. A Sputnik DAO executes an upgrade in the same call as its deciding vote. There is no timelock to wait out. Keyhole watches those proposals, reads the code they would install, and grades it while there is still time. If you armed an escape hatch, Keyhole can submit your exit before the upgrade executes when the window allows; that is not guaranteed (see what it does not do). Every answer comes with the request that proves it.

See it coming

An upgrade proposal names the exact code hash. For UpgradeRemote and UpgradeSelf, a store_blob transaction to the DAO holds the bytes, and it must be on chain before the proposal executes; near-plugins deploys stage the code on the contract. When Keyhole finds those bytes, it can read them before the proposal executes.

Grade it before it runs

New methods and privileged host calls, diffed against the live code. The source the bytes declare, SourceScan and reproducible builds. A private review in a NEAR AI Cloud TEE, with a receipt.

Get out first

A withdraw-to-yourself you signed in advance, relayed the moment Keyhole says STOP. The guardian pays the gas and the 1 yoctoNEAR. It cannot change a field of what you signed; the venue's code at that moment decides where the money goes.

What it does not do

        
Keyhole describes and acts on public facts. It is not an audit, and it does not accuse anyone: most upgrades are routine.

        
    
          
  • No window, no head start. A change staged and deployed in one transaction, a direct redeploy by a key, or an unrestricted upgrade path leaves nothing to beat. Keyhole then alerts after the fact, within seconds.
    • 
          
  • Bytes, not intent. The diff sees new methods and privileged host calls. A logic change inside an existing method (a withdraw that keeps half) is invisible to it; that is what the private review and verified builds are for.
    • 
          
  • Native NEAR, not tokens. A money path means native NEAR leaving the contract. Token balances, such as Ref and Burrow deposits, move with ft_transfer calls the diff does not flag: an upgrade that sends everyone's tokens out grades CAUTION if its code is unverified (OK if verified) unless an AI review says high risk, so a stop hatch would not fire.
    • 
          
  • AI can raise an upgrade verdict, not lower it. For a pending upgrade, a high-risk AI review alone is enough for STOP, which fires stop hatches. No AI review lowers an upgrade verdict.
    • 
          
  • Your own keys. A hatch cannot help if a key on your account is compromised: any full-access key can delete it first.
    • 
          
  • Off-chain trigger. The guardian decides when to submit. The worst it can do is send the exit you signed early, late or never. In this build it also fires on STOP for code that already landed; the exit then runs the new code, which decides where the funds go.
    • 
          
  • A TEE receipt is provenance. It proves which model answered inside an attested enclave, over exactly which request. It does not prove the answer is right.
    • 
          
  • Agents get a check, not a signer. @keyhole/guard refuses the call in code, before signing, when the live code or a pending upgrade grades STOP. The Keyhole MCP server is read-only: none of its tools takes a key or sends a transaction.
    • 
          
  • Testnet for the action. The radar reads mainnet. Hatches are demonstrated on testnet; nothing here signs on mainnet.
